# PRODUCT_SPEC — «Управленческий AI-аудит компании»

**Версия:** RU-1.0 (спецификация для реализации standalone-приложения)  
**Статус:** рабочая продуктовая спецификация для разработки  
**Основа:** существующее описание продукта «AI Company Audit iTeam» и утверждённый `ARCHITECTURE.md`.

## 0. Нормативный статус и порядок приоритетов

Этот документ определяет **что именно должен делать продукт**: пользовательские сценарии, содержимое диагностики, расчёты, отчёт, PDF, Dashboard, административную панель, аналитику и критерии готовности.

`ARCHITECTURE.md` определяет **как продукт должен быть реализован технически**: модульные границы, физическую схему данных, Supabase Auth/RLS, серверные интеграции, фоновые задания, безопасность, версионирование и эксплуатационные требования.

При расхождении документов действует следующий порядок:

1. Бизнес-логика, тексты, формулы, шкалы, структура отчёта и критерии MVP — по `PRODUCT_SPEC.md`.
2. Техническая реализация, безопасность, физическая модель БД, права доступа и инфраструктурные паттерны — по `ARCHITECTURE.md`.
3. Нельзя изменять формулы, вопросы, смысл отчёта или пользовательские сценарии ради упрощения реализации.
4. Нельзя ослаблять требования безопасности ради буквального повторения Bubble.
5. Если конкретное правило отсутствует в обоих документах, Codex не должен его придумывать: нужно пометить его как `TODO / requires product decision`.

## 0.1. Согласованные технические уточнения

- Продукт является самостоятельным приложением и не зависит от Bubble.
- На старте весь пользовательский интерфейс — русский; архитектура должна оставаться готовой к будущей локализации.
- Для MVP используется текущая бизнес-модель **один пользователь → одна основная компания**: повторное сохранение профиля обновляет существующую Company, а не создаёт новую. Техническая схема может позволять расширение до нескольких компаний позднее.
- Пароли не хранятся в прикладной таблице `User`: идентификацией и хранением credentials управляет Supabase Auth согласно `ARCHITECTURE.md`.
- Раздел «Модель данных» ниже является **логической продуктовой моделью**. Физическую реляционную схему нужно строить по `ARCHITECTURE.md`.
- Смысловые разделы AI-ответа `[SUMMARY]`, `[MAIN_DIAGNOSIS]` и т. п. сохраняются как контракт отчёта, но технически предпочтителен валидируемый Structured Output/JSON, а не парсинг свободного текста по маркерам.
- Математические показатели рассчитывает детерминированный scoring engine. AI не имеет права рассчитывать или подменять индекс, BlockScore или maturity level.
- PDF генерируется на сервере из сохранённой версии отчёта; не требуется воспроизводить Bubble screenshot-to-PDF.
- Доступность из Российской Федерации является обязательным release gate. Если выбранные Vercel/Supabase/CDN/шрифты или другие критические зависимости нестабильны у российских провайдеров, инфраструктуру необходимо заменить до production-запуска.
- Отправка отчёта по email может поддерживаться архитектурой, но в исходном критерии MVP ниже обязательным пользовательским артефактом является PDF. Email-доставка отчёта не должна блокировать MVP без отдельного подтверждения.
- Отдельная «административная оценка диагностики» не описана в исходной продуктовой спецификации. Пользовательский Feedback/«Оценить аудит» является обязательным. Дополнительную admin-assessment механику не вводить без отдельного решения.

## 0.1.1. Источник истины для методики RU-1.0

Для точных формулировок и метаданных диагностических вопросов источником истины является файл `METHODOLOGY_RU_1_0.csv`, подготовленный по актуальным экспортам Bubble от 2026-09-10.

При расхождении текста вопроса, названия блока или метаданных между этим документом и `METHODOLOGY_RU_1_0.csv` используется значение из `METHODOLOGY_RU_1_0.csv`.

Файл содержит 10 блоков и 84 вопроса: 80 оценочных вопросов в 8 блоках и 4 текстовых вопроса в служебных блоках `company_info` и `open_questions`. Все 80 оценочных вопросов имеют вес 1, все 8 оценочных блоков имеют вес 1, все 84 вопроса активны, `reverse_score=false` для всех вопросов; 82 вопроса обязательны, 2 финальных открытых вопроса необязательны.

`METHODOLOGY_RU_1_0_CHANGES.csv` хранит прозрачный журнал только технических исправлений: очевидных опечаток, whitespace и нормализации `ai_context_label`. Исходные Bubble label и unique id сохраняются для трассировки.

## 0.2. Требования, которых не хватает в исходном описании и которые нельзя выдумывать

Перед завершением соответствующих модулей необходимо получить/подтвердить:

- точный перечень **открытых вопросов** (в документе указано, что они есть, но их тексты не приведены);
- точные `weight`, `is_required`, `is_active`, `reverse_score` и другие метаданные для каждого вопроса, если они отличаются от единичных/стандартных значений;
- веса восьми блоков, если они не одинаковые;
- поведение для пропущенных / неприменимых вопросов;
- точный режим округления и правило: maturity level определяется по raw-индексу или по отображаемому округлённому индексу;
- точный production AI prompt: исходный документ заканчивается заголовком `AI PROMPT`, но текст промпта в нём отсутствует;
- политика срока жизни незавершённой диагностики и одновременных попыток;
- требования к миграции исторических данных из Bubble;
- юридические версии политик/согласий и срок хранения персональных данных.

# Подробные продуктовые требования


## 1. Назначение продукта
Веб-приложение предназначено для собственников, генеральных директоров и руководителей компаний. Пользователь проходит структурированную диагностику системы управления компанией, после чего получает:
- интегральный Индекс управляемости от 0 до 100%;
- уровень управленческой зрелости;
- оценку по 8 элементам системы управления;
- системный управленческий диагноз;
- сильные стороны;
- ключевые проблемные зоны;
- главное ограничение роста;
- риски внедрения изменений;
- первоочередные действия;
- план улучшений на 30, 60 и 90 дней;
- итоговый PDF-отчёт;
- возможность оставить заявку на консультацию;
- возможность оценить качество продукта.
Ключевая ценность продукта — не просто выдать баллы, а на основании результатов диагностики сформировать с помощью LLM персонализированный управленческий отчёт уровня бизнес-консультанта.
Продукт должен быть полностью независим от Bubble.

## 2. Основная логика
Общий пользовательский путь:
Лендинг → регистрация → профиль компании → диагностика → расчёт результатов → AI-анализ → отчёт → PDF → обратная связь / заявка на консультацию
Повторный пользователь:
Вход → личный кабинет → новая диагностика / продолжение незавершённой / просмотр предыдущих отчётов
Администратор:
Вход → административная панель → пользователи / компании / диагностики / отчёты / заявки / отзывы / воронка


### 2.1. Логика перемещения пользователя по страницам приложения

Ниже описана навигационная логика пользовательской части. Она развивает уже зафиксированный пользовательский путь и должна рассматриваться как часть продуктового поведения, а не только как рекомендация по UI.

#### 2.1.1. Базовые состояния пользователя

Система должна различать как минимум следующие состояния:

1. Неавторизованный пользователь.
2. Авторизованный пользователь без заполненного профиля компании.
3. Авторизованный пользователь с профилем компании, но без начатой диагностики.
4. Авторизованный пользователь с незавершённой диагностикой.
5. Авторизованный пользователь с завершённой диагностикой, по которой формируется отчёт.
6. Авторизованный пользователь с готовым отчётом.
7. Администратор.

Переходы между страницами зависят не только от URL, но и от текущего состояния пользователя и диагностики.

#### 2.1.2. Публичная часть

Основной публичный маршрут:

```text
Лендинг
  ↓
Регистрация
  ↓
Профиль компании
  ↓
Dashboard
```

Если неавторизованный пользователь нажимает «Перейти к диагностике», система направляет его на регистрацию.

Если пользователь уже зарегистрирован, со страницы регистрации должна быть доступна ссылка «Войти».

Если пользователь уже авторизован и открывает лендинг, рекомендуется направлять его в Dashboard.

#### 2.1.3. Регистрация

После успешной регистрации новый пользователь не должен сразу попадать в диагностику.

Переход:

```text
Регистрация
  ↓
Профиль компании
```

Если подтверждение email включено как обязательное требование, между этими шагами добавляется состояние:

```text
Регистрация
  ↓
Подтверждение email
  ↓
Профиль компании
```

Точный момент обязательности email verification должен соответствовать принятой authentication policy.

Если пользователь покинул приложение после регистрации, но до заполнения профиля компании, при следующем входе его необходимо вернуть на страницу профиля компании, а не в пустой Dashboard.

#### 2.1.4. Первый вход после заполнения профиля компании

После успешного сохранения профиля:

```text
Профиль компании
  ↓
Dashboard
```

Dashboard является основной точкой входа в авторизованную пользовательскую часть приложения.

На Dashboard пользователь видит:

- свою компанию;
- кнопку начала новой диагностики;
- незавершённую диагностику, если она существует;
- историю завершённых диагностик;
- ссылки на доступные отчёты.

#### 2.1.5. Начало новой диагностики

При нажатии «Новая диагностика»:

```text
Dashboard
  ↓
Создание Diagnostic
  ↓
Первый блок диагностики
```

Диагностика создаётся до показа первого вопроса, чтобы ответы и прогресс можно было сохранять с самого начала.

Новая диагностика должна быть привязана к:

- текущему пользователю;
- компании;
- конкретной опубликованной версии методики;
- дате начала;
- текущему блоку.

Если продукт в дальнейшем разрешит несколько одновременных незавершённых диагностик, эта логика должна быть утверждена отдельно. Для MVP не следует создавать дубликаты попыток случайным повторным нажатием кнопки.

#### 2.1.6. Перемещение внутри диагностики

Диагностика состоит из последовательности блоков.

Основной сценарий:

```text
Блок 1
  ↓
Блок 2
  ↓
...
  ↓
Блок 8
  ↓
Открытые вопросы
  ↓
Завершение диагностики
```

На каждом блоке пользователь должен иметь возможность:

- выбирать ответы;
- сохранять ответы;
- перейти к следующему блоку;
- вернуться к предыдущему блоку;
- покинуть диагностику и продолжить её позже.

Перед переходом на другой блок все изменённые ответы текущего блока должны быть сохранены.

Кнопка «Назад» внутри диагностики возвращает на предыдущий диагностический блок, а не должна зависеть от browser history.

Кнопка «Далее» переводит на следующий блок только после успешного сохранения текущих изменений.

Если обязательные вопросы проверяются на уровне блока, пользователь получает локальные ошибки до перехода. Если текущая методика предполагает итоговую проверку обязательности только при завершении, система должна разрешать переход между блоками и выполнить полную проверку перед Submit. Точное правило должно соответствовать методике.

#### 2.1.7. Выход из незавершённой диагностики

Если пользователь уходит в Dashboard:

```text
Диагностика
  ↓
Dashboard
```

диагностика остаётся в статусе «В процессе».

На Dashboard должна появиться заметная карточка:

```text
Незавершённая диагностика
[Продолжить]
```

Нажатие «Продолжить» возвращает пользователя не на первый блок, а на последний сохранённый/current block.

Если пользователь закрывает вкладку или браузер, после следующего входа применяется та же логика.

#### 2.1.8. Прямое открытие URL диагностики

Если авторизованный пользователь открывает URL своей незавершённой диагностики, система должна открыть её на сохранённом текущем блоке.

Если диагностика уже завершена, редактирование ответов запрещено. Пользователь должен быть перенаправлен:

- на страницу результата/отчёта, если отчёт готов;
- на страницу состояния генерации, если отчёт ещё формируется;
- на страницу результата с сообщением об ошибке, если AI-генерация завершилась ошибкой.

Пользователь никогда не должен иметь возможность открыть чужую диагностику изменением ID в URL.

#### 2.1.9. Завершение диагностики

На последнем этапе пользователь нажимает кнопку завершения диагностики.

Сценарий:

```text
Последний блок / открытые вопросы
  ↓
Проверка обязательных ответов
  ↓
Расчёт BlockScore
  ↓
Расчёт ManageabilityIndex
  ↓
Определение maturity level
  ↓
Запуск генерации AI-отчёта
```

Если обязательные ответы отсутствуют, диагностика не завершается.

Пользователь должен получить понятное сообщение и возможность перейти к месту, где остались незаполненные обязательные вопросы.

После успешного Submit ответы становятся недоступными для обычного редактирования.

#### 2.1.10. Состояние генерации отчёта

После завершения диагностики пользователь не должен возвращаться на экран вопросов.

Он переходит на экран/страницу ожидания:

```text
Диагностика завершена
  ↓
Готовим отчёт о результатах диагностики...
```

Экран показывает:

- статус генерации;
- счётчик прошедшего времени;
- сообщение, что пользователь может дождаться результата;
- корректное состояние ошибки, если генерация не удалась.

Если AI-генерация завершилась успешно:

```text
Генерация
  ↓
Страница отчёта
```

Переход может выполняться автоматически после получения статуса `report ready`.

Если пользователь закрыл страницу во время генерации, процесс не должен прерываться. После повторного входа Dashboard должен показывать актуальный статус диагностики/отчёта.

#### 2.1.11. Ошибка генерации AI

При ошибке:

```text
Генерация
  ↓
Ошибка AI
```

Пользователь должен видеть:

- что сама диагностика успешно завершена;
- рассчитанный индекс и maturity level, если они уже доступны;
- понятное сообщение об ошибке;
- возможность повторить генерацию отчёта.

Нельзя возвращать пользователя к повторному прохождению 80 вопросов только из-за ошибки AI.

#### 2.1.12. Страница отчёта

Основной маршрут после готовности:

```text
Dashboard
  ↓
История диагностик
  ↓
Отчёт
```

или:

```text
Завершение диагностики
  ↓
Генерация отчёта
  ↓
Отчёт
```

Со страницы отчёта пользователь может:

- скачать PDF;
- оставить заявку на консультацию;
- при разрешённой логике повторно сформировать AI-отчёт;
- вернуться в Dashboard.

Повторная генерация создаёт новую версию Report и не должна менять исходные ответы, BlockScore, ManageabilityIndex или maturity level.

#### 2.1.13. Повторная диагностика

После завершённой диагностики пользователь может начать новую:

```text
Отчёт
  ↓
Dashboard
  ↓
Новая диагностика
```

или непосредственно из Dashboard.

Новая диагностика создаёт новую запись `Diagnostic`.

Ответы предыдущей диагностики автоматически не переносятся в новую.

Исторические отчёты остаются доступны.

#### 2.1.14. Редактирование профиля компании

Профиль компании доступен из авторизованной части приложения.

Переход:

```text
Dashboard
  ↓
Профиль компании
  ↓
Сохранить
  ↓
Dashboard
```

Изменения профиля влияют на будущие диагностики.

Они не должны ретроспективно изменять company snapshot уже завершённых диагностик и сформированные исторические отчёты.

#### 2.1.15. Feedback / «Оценить аудит»

После появления хотя бы одной завершённой диагностики пользователь получает возможность открыть форму «Оценить аудит».

Сценарий:

```text
Dashboard или Report
  ↓
Оценить аудит
  ↓
Popup / форма Feedback
  ↓
Спасибо за обратную связь
  ↓
Исходная страница
```

Feedback не должен изменять статус диагностики или отчёта.

Если пользователь уже оставил предусмотренный продуктом отзыв, повторный CTA может быть скрыт.

#### 2.1.16. Заявка на консультацию

Основной сценарий:

```text
Report
  ↓
Получить консультацию
  ↓
Форма
  ↓
Отправка
  ↓
Popup благодарности
  ↓
Report
```

Отправка заявки не должна уводить пользователя со страницы отчёта и не влияет на сам Report.

#### 2.1.17. Вход повторного пользователя

После обычного входа система проверяет состояние аккаунта.

Логика:

```text
Login
  ↓
Есть профиль компании?
  ├─ Нет → Профиль компании
  └─ Да → Dashboard
```

На Dashboard:

```text
Есть незавершённая диагностика?
  ├─ Да → показать «Продолжить»
  └─ Нет → показать «Новая диагностика»
```

Автоматически открывать незавершённую диагностику сразу после login не обязательно: пользователь должен видеть Dashboard и осознанно выбрать «Продолжить», если иное не будет утверждено отдельно.

#### 2.1.18. Защищённые маршруты

Неавторизованный пользователь не может открывать:

- Dashboard;
- профиль компании;
- диагностику;
- Report;
- административные страницы.

При попытке открыть защищённый URL:

```text
Protected URL
  ↓
Login
```

После успешного входа допустим возврат на исходный URL только если пользователь имеет право его открыть.

#### 2.1.19. Административная навигация

Администратор после входа имеет отдельную точку входа:

```text
Login
  ↓
Admin Dashboard
```

Основные разделы:

```text
Admin Dashboard
├── Пользователи
├── Компании
├── Диагностики
├── Отчёты
├── Заявки
├── Feedback
└── Воронка
```

Из списков должны быть доступны переходы к детальным карточкам/просмотрам соответствующих сущностей.

Обычный пользователь при попытке открыть `/admin/...` получает отказ в доступе и не должен видеть административные данные.

Если администратор одновременно имеет обычный пользовательский аккаунт, переход между пользовательской и административной частью можно реализовать отдельным пунктом меню; точный UX можно определить на этапе UI.

#### 2.1.20. Logout

После выхода:

```text
Любая авторизованная страница
  ↓
Logout
  ↓
Лендинг или Login
```

После logout защищённые страницы не должны оставаться доступными через Back без повторной проверки сессии.

## 11. Восемь блоков диагностики

### 11.1. Стратегия
1. У компании есть ясное направление развития на ближайшие 1–3 года.
1. Управленческая команда одинаково понимает стратегические приоритеты компании.
1. Компания определила ограниченное число приоритетов, на которых действительно концентрирует ресурсы.
1. Стратегические цели основаны на понимании клиентов, рынка и конкурентной среды.
1. Компания ясно понимает, за счёт каких конкурентных преимуществ она планирует развиваться.
1. При принятии крупных решений руководство использует стратегические приоритеты как критерий выбора.
1. Бюджеты, инвестиции и ключевые ресурсы распределяются в соответствии со стратегическими приоритетами.
1. Для реализации стратегии определены конкретные стратегические инициативы и ответственные за них.
1. Руководство регулярно проверяет ключевые предположения, на которых построена стратегия.
1. Стратегия регулярно пересматривается при существенных изменениях рынка и положения компании.

### 11.2. Организационная структура
1. Для каждого подразделения ясно определены его функции и зона ответственности.
1. Руководители понимают, за какие конечные результаты они персонально отвечают.
1. Полномочия руководителей соответствуют возложенной на них ответственности.
1. В компании понятно, кто имеет право принимать основные типы управленческих решений.
1. Между подразделениями нет существенного дублирования функций и ответственности.
1. Ключевые участки деятельности компании не остаются без явно назначенного владельца.
1. Количество уровней управления соответствует масштабу и сложности бизнеса и не создаёт лишних задержек.
1. Руководители имеют управляемое количество непосредственных подчинённых.
1. Организационная структура соответствует текущей стратегии и бизнес-модели компании.
1. При возникновении межфункциональных вопросов понятно, кто принимает окончательное решение и отвечает за результат.

### 11.3. Бизнес-процессы
1. Ключевые процессы компании определены от начала до конечного результата.
1. Для каждого критически важного процесса назначен владелец, отвечающий за его результат целиком.
1. Участники ключевых процессов понимают последовательность действий и свою роль.
1. Правила передачи работы и информации между подразделениями определены и соблюдаются.
1. Для повторяющихся операций существуют понятные стандарты и регламенты.
1. Ключевые процессы имеют измеримые показатели качества, скорости, стоимости или результата.
1. Руководство знает основные узкие места и причины задержек.
1. Отклонения и сбои анализируются системно, а не только устраняются вручную.
1. Процессы регулярно совершенствуются на основе данных и выявленных проблем.
1. Ключевые процессы построены исходя из конечного результата для клиента.

### 11.4. Цели и показатели
1. У компании определены измеримые цели на текущий год.
1. Цели подразделений непосредственно связаны с целями компании.
1. Руководители понимают, какие показатели отражают их вклад в общий результат.
1. Для ключевых показателей установлены целевые значения и сроки.
1. За каждый ключевой показатель назначен ответственный руководитель.
1. Есть и итоговые, и опережающие показатели.
1. Данные по ключевым показателям доступны своевременно и вызывают доверие.
1. Показатели разных подразделений не стимулируют противоречащие решения.
1. Руководители регулярно сопоставляют факт с планом.
1. Существенные отклонения приводят к конкретным управленческим решениям.

### 11.5. Управленческий ритм
1. Есть регулярный цикл планирования, контроля и корректирующих действий.
1. Руководители регулярно рассматривают выполнение планов и KPI.
1. Совещания сосредоточены на отклонениях, причинах и решениях.
1. По итогам фиксируются решения, ответственные, сроки.
1. Выполнение решений контролируется.
1. Проблемы своевременно эскалируются.
1. Прогнозы и планы корректируются при изменении ситуации.
1. Межфункциональные вопросы рассматриваются совместно.
1. Календарь управленческих циклов определён и соблюдается.
1. Система управления позволяет контролировать компанию без постоянного ручного вмешательства первого лица.

### 11.6. Команда
1. В управленческой команде есть необходимые компетенции.
1. Руководители самостоятельно принимают решения в пределах полномочий.
1. Команда открыто обсуждает сложные вопросы.
1. После решения руководители его поддерживают и действуют согласованно.
1. Руководители действуют как единая команда, а не только защищают свои функции.
1. Первое лицо делегирует значительную часть операционных вопросов без потери управляемости.
1. Руководители уделяют время развитию бизнеса и системы управления, а не только операционной деятельности.
1. Компания системно развивает управленческие компетенции.
1. Есть кадровый резерв/преемники на ключевые позиции.
1. Команда поддерживает стабильную работу без постоянного личного вмешательства собственника/генерального директора.

### 11.7. Мотивация и ответственность
1. Каждый руководитель понимает персональную ответственность за результат.
1. Сотрудники понимают ожидаемые результаты и критерии оценки.
1. Полномочий и ресурсов достаточно для ответственности.
1. Вознаграждение поддерживает цели компании.
1. Переменная часть руководителей связана с измеримыми результатами.
1. Хорошие результаты получают заметное признание.
1. Невыполнение обязательств имеет понятные последствия.
1. Руководители регулярно дают содержательную обратную связь.
1. При проблеме понятно, кто отвечает за решение до результата.
1. Не принято перекладывать ответственность.

### 11.8. Корпоративная культура
1. Руководители своим поведением демонстрируют ожидаемые принципы.
1. Принято открыто говорить о проблемах.
1. Ошибки используются для анализа причин и улучшения системы, а не поиска виновных.
1. Сотрудники могут предлагать улучшения.
1. Подразделения сотрудничают ради общего результата.
1. Решения руководства последовательны и предсказуемы.
1. Ценится выполнение обязательств.
1. Организация быстро меняет способы работы при изменении среды.
1. Важные решения и причины прозрачно объясняются.
1. Реальное поведение соответствует заявленным ценностям.

## 12. Шкала ответов и расчёт
В текущей модели вопрос имеет внутреннюю шкалу:
0–4
Максимум — 4.
Если интерфейс показывает пользователю 5 кнопок 1–5, необходимо явно реализовать маппинг:
1 → 0<br>2 → 1<br>3 → 2<br>4 → 3<br>5 → 4
Это важно, чтобы сохранить существующие значения индекса.
Для reverse_score = true:
effective_score = 4 - score
В текущем наборе основных вопросов все формулировки сделаны в позитивном направлении, поэтому обратная шкала практически не используется.

## 13. Расчёт оценки блока
Для каждого из 8 основных блоков:
BlockScore = сумма взвешенных баллов / максимально возможная сумма × 100
При весе всех вопросов = 1 и 10 вопросах:
BlockScore = средний балл / 4 × 100
Например:
средний внутренний балл 2.8
даёт:
2.8 / 4 × 100 = 70%

## 14. Общий Индекс управляемости
Общий индекс — среднее значение оценок 8 основных управленческих блоков.
При одинаковом весе:
ManageabilityIndex = (B1 + B2 + ... + B8) / 8
Пример из текущей диагностики:
- Стратегия — 70%;
- Структура — 62,5%;
- Процессы — 57,5%;
- Цели — 62,5%;
- Ритм — 65%;
- Команда — 67,5%;
- Мотивация — 70%;
- Культура — 55%.
Индекс:
63,75%
В интерфейсе и отчётах отображается:
63,8%
То есть расчёты хранятся с полной точностью, отображение — 1 знак после запятой.

## 15. Уровни управленческой зрелости
Текущая шкала:

| Индекс | Уровень |
| --- | --- |
| < 30 | Критическая зона |
| 30–49,9 | Слабая зона |
| 50–69,9 | Зона развития |
| 70–84,9 | Зрелая зона |
| ≥ 85 | Сильная зона |

Пороги желательно хранить как конфигурацию, а не жёстко вшивать в UI.

- Черновик;
- В процессе;
- Отправлена;
- Дана оценка;

## 18. Требования к AI
Модель должна выступать в роли опытного консультанта по:
- системному управлению;
- организационному развитию;
- бизнес-процессам;
- стратегическому исполнению;
- масштабируемости бизнеса.
Основные правила:
- не придумывать факты;
- основывать выводы на входных данных;
- отличать факты от диагностических выводов;
- отдельно обозначать рекомендации, основанные на best practice;
- искать системные причины, а не просто перечислять низкие баллы;
- показывать взаимосвязи между блоками;
- отличать симптомы от корневых причин;
- не преувеличивать проблемы;
- признавать сильные стороны;
- если данных недостаточно — писать о гипотезе, а не о доказанном факте;
- значения процентов — максимум один знак после запятой;
- не писать, что отчёт создан AI;
- не объяснять внутреннюю методологию;
- избегать рекламных и мотивирующих клише;
- избегать непонятного консультантского жаргона;
- не использовать необъяснённые SIPOC, RACI, SLA, BPMN и аналогичные сокращения;
- писать понятным языком для собственника или CEO.
Объём ориентировочно:
1000–1500 слов.

## 19. Структура AI-ответа
Модель должна возвращать текст с техническими маркерами:
[SUMMARY]
[MAIN_DIAGNOSIS]
[MANAGEABILITY_INDEX_TEXT]
[STRENGTHS]
[KEY_PROBLEM_ZONES]
[GROWTH_CONSTRAINT]
[IMPLEMENTATION_RISKS]
[FIRST_ACTIONS]

Особенно:

не должен быть пустым.

## 20. Смысл разделов отчёта
Резюме
Общая ситуация, зрелость, сильные стороны и основное ограничение.
Основной диагноз
Центральная системная управленческая проблема.
Желательно структурировать:
- факты;
- выводы из результатов диагностики;
- рекомендации на основе управленческой практики.
Что означает индекс
Практическая интерпретация значения индекса и уровня зрелости.
Сильные стороны
3–5 факторов.
Не следует автоматически считать сильной стороной:
- возраст компании;
- размер;
- выручку;
- количество уровней управления.
Ключевые проблемные зоны
3–5 проблем, ранжированных по влиянию.
Для каждой:
- слабость;
- почему важна;
- последствия;
- связь с другими результатами.
Главное ограничение роста
Одна ключевая проблема + причинный механизм её влияния на масштабирование.
Риски внедрения
Что может сорвать улучшения.
Первые действия
Только 3 основных действия.
30 / 60 / 90 дней
Не более примерно 4 приоритетных результатов на период.
Следующий шаг
Что делать после первоначального 90-дневного цикла.

## 33. AI-провайдер
Не следует жёстко привязывать архитектуру приложения к одному LLM.
Нужен серверный интерфейс условно:
AIReportProvider
например:
generateReport(input): ReportSections
Первоначально можно использовать OpenAI, но архитектура должна позволять заменить его другим провайдером без переписывания бизнес-логики.
Это особенно важно для русской версии.
API-ключи хранятся только на сервере.

## 34. Ошибки AI
Backend обязан корректно обрабатывать:
- 400 — неправильный запрос;
- 401 — ключ;
- 429 — rate limit / недостаток баланса;
- 5xx;
- timeout;
- неправильный формат ответа;
- отсутствие обязательной секции.
Нельзя показывать пользователю raw JSON или технические ошибки провайдера.
Пользовательское сообщение:
Не удалось сформировать отчёт. Попробуйте ещё раз или обратитесь в поддержку.
Полная техническая ошибка сохраняется в log.

## 35. Безопасность
Обязательно:
- HTTPS;
- безопасное хеширование паролей (Argon2id или bcrypt);
- CSRF-защита;
- rate limiting login/reset;
- серверное хранение API secrets;
- проверка прав доступа на backend;
- пользователь никогда не может получить чужую Company/Diagnostic/Report через подмену ID;
- журналирование административных ошибок;
- резервные копии БД.

Обязательное согласие и необязательное маркетинговое согласие должны храниться отдельно.

## 37. Инфраструктурное требование для российской версии
Это принципиально.
Причина разработки самостоятельного клона — в том числе невозможность стабильного доступа пользователей из РФ к Bubble/Cloudflare.
Поэтому перед запуском разработчик должен обязательно протестировать весь сервис из России минимум через несколько крупных операторов.
Необходимо исключить критическую зависимость frontend от инфраструктуры, которая массово ограничивается российскими провайдерами.
Проверить:
- HTML;
- JS bundles;
- CDN;
- шрифты;
- CSS;
- изображения;
- API;
- WebSocket, если используется;
- PDF;
- authentication.
Сайт не должен загружать критически необходимые ресурсы с Bubble.

- idempotency генерации отчёта;
- нормальный background job для AI/PDF;
- возможность смены AI-провайдера.

## 44. Версионирование методики
Очень рекомендую добавить:
QuestionSetVersion
Например:
RU-1.0
Каждая Diagnostic должна знать, по какой версии вопросов она была проведена.
Аналогично:
PromptVersion
Например:
report-ru-1.3
Report хранит версию prompt.
Это позволит через год понять, какой набор вопросов и какой prompt сформировали конкретный отчёт.

## 45. Критерии готовности MVP
Продукт считается воспроизведённым, если новый пользователь может без ручного вмешательства администратора пройти полный путь:
Лендинг<br>→ регистрация<br>→ профиль компании<br>→ 80 вопросов<br>→ открытые вопросы<br>→ сохранение<br>→ расчёт 8 блоков<br>→ индекс<br>→ maturity level<br>→ AI<br>→ структурированный отчёт<br>→ PDF<br>→ заявка<br>→ feedback
Администратор при этом видит:
User<br>→ Company<br>→ Diagnostic<br>→ Report<br>→ LeadRequest<br>→ Feedback
И все показатели рассчитываются так же, как в текущем приложении.

**AI PROMPT:** в исходном файле после этого заголовка текст промпта отсутствует; точный production prompt должен быть добавлен отдельной утверждённой версией.

# 47. Критерий начала программирования

Разработка может начаться с Foundation/Authentication/Company Profile, потому что эти части не требуют недостающей методологии.

Реализацию финального scoring engine нельзя считать завершённой, пока не подтверждены все веса, requiredness, missing-answer semantics и правило классификации maturity на граничных значениях.

Production AI-интеграцию нельзя считать завершённой, пока не утверждён точный prompt или его эквивалентный versioned structured-output contract.

Production deployment нельзя считать завершённым без проверки полного пользовательского пути из Российской Федерации.
