# Ограниченная retention-очистка

Только ручной операторский процесс; расписание и автоматический purge при запуске web/worker не установлены. До production-разрешения исполнитель ограничен staging. Ответственный оператор выполняет dry-run и согласованную очистку ежедневно, разбирает пропуски/holds и ведёт count-only квитанции. Отсутствие регулярного исполнения — операционное нарушение, а не доказательство соблюдения сроков.

`public.run_retention_maintenance` доступен только service_role, по умолчанию dry-run, 1–500 записей **на категорию** за транзакцию. Категории: anonymous_sessions, product_events, email_deliveries, consultation_deliveries. Границы: expires_at <= now; события старше 12 календарных месяцев; завершённые/неуспешные доставки старше 12 месяцев с учётом последней активности. Активные доставки сначала разбирает оператор; не гасить живые задания ради очистки. Явный private.retention_holds исключает запись до документированного снятия; review_at требует проверки, не автоматически снимает hold.

Скрипт `scripts/retention-maintenance.ts` с заранее приватно предоставленными APP_URL, SUPABASE_URL и service-role credential печатает только счётчики. Без --apply выполняется только предварительный подсчёт. --batch ограничивает каждую категорию. Для --apply на staging обязателен JSON --scope с точными ID **новых синтетических фикстур**. Пустой/отсутствующий список категории означает ноль, а не все записи. Глобальный scope на staging разрешён только для dry-run. Продолжать порциями до нулевого dry-run, каждый раз сверяя scope и protected fingerprints; при неожиданном результате остановиться.

Квитанция dry-run содержит точные количества выбранной порции; глобальный backlog при необходимости подсчитывается отдельным COUNT без выгрузки содержимого. Конкурирующие заблокированные строки пропускаются и попадут в следующий проход. Функция блокирует выбранные строки и сериализует maintenance-вызовы. Claimed и любой связанный с диагностикой/Account tombstone исключены, бизнес-таблицы не входят в целевые UPDATE/DELETE. Ответы/контекст/контакты/секреты просроченной незаявленной сессии стираются, остаётся минимальный tombstone для immutable consent evidence. Удаление старого product_event не удаляет его Account/Diagnostic. Email-минимизация сохраняет ссылки, статус и даты, удаляет адрес получателя/ID провайдера/ошибки; никаких PDF и чеков не удаляет.

Сфера журналов: report email и consultation notification deliveries. Anonymous email использует поля временной сессии и очищается вместе с ней. Team invitation/reservation — действующие бизнес-/auth-данные, не отдельный delivery log; их удаление относится к проверенному запросу субъекта, не к этому возрастному purge. Идентификаторы связей email tombstone остаются персональными при возможности сопоставления и регулируются сроком Account/запросом удаления, а не объявляются полностью анонимными.

Исторические user_consents и anonymous_diagnostic_consents неизменяемы. Withdrawals — отдельный append-only след; marketing_preferences запрещает будущие маркетинговые отправки, не сервисные. Удаление Account/Team — по отдельной ручной процедуре, без удаления чужих общих данных и обязательных финансовых записей. Production-включение исполнителя/расписания и реальные запросы на удаление требуют отдельного плана; в этом релизе production не меняется.
