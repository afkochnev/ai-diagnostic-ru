# V2.1A — Account and multi-company foundation

Prepared locally on 2026-10-12, based on reconciliation commit
`0996971bfeac4ab50136998307169f6c63be8f44`. Production application baseline remains
`0b8c4acb6a1071e5be06268ba8216c4215036e84` until a separately authorized rollout.
No remote migration, methodology ledger repair or deployment is part of this stage.

## Preflight and implementation plan

Read-only staging/production preflight confirmed 30 recorded migrations,
manageability v3 retired and v4 published, with no account tables yet. Existing
company, diagnostic and identity policies/provisioning were reviewed. All existing
methodology migration files and v3/v4 row content are untouched.

1. Phase A adds account tables and a nullable company account FK, then provisions
   and verifies the legacy mapping in one transaction. V1 uniqueness/policies stay.
2. Deploy the compatible application in a future rollout: current memberships
   authorize resources; company IDs become explicit; zero/one-company entry points
   remain usable; multiple companies require selection.
3. Phase B validates the company FK, enforces NOT NULL, replaces legacy RLS and
   removes only the obsolete unique owner constraint. This is applied only after
   compatible application paths have been validated.
4. Verify the clean/upgrade paths, immutable legacy row snapshots, RLS/IDOR,
   signup, concurrency boundaries and full application checks before operator review.

## Schema

### public.accounts

UUID PK generated by PostgreSQL; nonempty name; active/archived status; optional,
unique `legacy_origin_user_id -> public.users(id)` with restrictive deletion;
created/updated timestamps. ID, origin and creation timestamp are immutable.
The origin identifies migration provenance, not continuing account authority.

### public.account_memberships

Composite PK `(account_id,user_id)` with restrictive account/user FKs. Only role
`owner` exists. Status is active/revoked with consistent `revoked_at`; `joined_at`
and both identity keys are immutable. A user can structurally own several accounts.

A partial unique account index permits at most one active owner. Deferred
constraint triggers require exactly one owner for an active account at commit.
Controlled operator transactions can archive+revoke, or replace the owner
atomically; no browser membership-management/transfer functionality is implemented.
The user/status/account index supports membership lookups.

### public.company_profiles

New `account_id` directly references accounts. Phase A adds a NOT VALID FK and
account/created_at/id index; Phase B validates it and enforces NOT NULL. No join
entity is needed. The original company PK and every incoming history FK survive.
`owner_user_id` remains immutable creator provenance; its nonunique index remains.
Only its unique constraint is removed in Phase B. A company cannot move accounts.

A BEFORE INSERT compatibility trigger supplies the unique legacy account for old
V1 payloads without account_id and validates the recorded creator's active owner
membership. Explicit new-company writes use explicit account context. Profile
updates use optimistic revision checks and cannot change ID, account, creator or
creation timestamp.

## Backfill and signup

The chosen strategy is random UUID plus a unique immutable legacy-origin mapping.
It avoids extension/namespace dependencies while making every subsequent replay
resolve the same account. Each public user receives one legacy account and one
active owner membership, including users without companies and administrators.
Each existing company attaches to the account mapped from its legacy owner.

`private.ensure_legacy_account(uuid)` and `private.backfill_legacy_accounts()` are
operator/provisioner-only. They never replace mappings, revive revoked memberships
or silently adopt another owner; incompatible state raises an error and rolls back.
Replaying backfill for the initial legacy state changes no IDs, memberships or
company metadata. This helper is not a general maintenance operation after
operator transfers/archiving or assignment to additional nonlegacy accounts.
Read-only catalog/mapping checks are the normal post-rollout verification.

Phase A locks auth.users before the source tables, so registrations wait before
starting the old trigger. Original consent validation, public identity, global
role=user and consent/audit inserts are retained; account provisioning is appended
inside the same Auth insert transaction. Untrusted signup metadata cannot choose
an existing account or elevate either role.

The company touch trigger preserves revision/updated_at when backfill changes
only account_id. No existing user, diagnostic, answer, snapshot, result, report,
PDF, email, lead, feedback, job or audit record is rewritten.

## Authorization and V1 compatibility

Verified cookie identity -> active owner membership -> active account -> company
-> diagnostic. Private RLS helpers have qualified objects, controlled search_path
and limited EXECUTE grants. Accounts/memberships allow browser SELECT only; users
cannot insert/promote/revoke themselves. Global administrator privileges remain
behind requireAdmin and MFA, and never imply account membership.

Phase B removes the old permissive policies rather than OR-combining authorities.
Answers, snapshots/results, report/PDF reads and save/submit RPCs use the account
chain. Retired pinned methodology reads use membership-aware access helpers only;
methodology content and ledger are unchanged. Numeric scoring/prompt/report/PDF
formats remain V1. Historical delivery/lead/feedback rows retain requester privacy;
feedback's original creator-consistency FK remains in place.

Server helpers bind supplied user IDs to the current verified cookie session.
Service-role PDF/email/regeneration operations check account authority before
exposing data or writing. PDF coalescing rechecks authority for every caller.
Save/submit retain existing RPC payloads and idempotency, with submission serialized
against saves. Lead replay checks current authority before duplicate returns.

Legacy dashboard/profile routes automatically resolve only an unambiguous company.
Explicit company pages and account/company lists handle multiple records without
an arbitrary first company. Profile/diagnostic forms carry IDs that are revalidated
on the server. Existing one-company users see the same dashboard content; admin
projections now list multiple companies through current memberships.

No extra-company creation control is shown for populated accounts. The server and
schema support explicit company creation; commercial limits are intentionally not
implemented. There are no plans, subscriptions, entitlements, billing/provider or
team entities in this stage.

## Risks and later rollout requirements

- Phase B requires compatible web code first. Rolling back to a singular-company
  binary after multiple records exist is unsafe; retain data and use compatible
  rollback code. Do not recreate the dropped owner uniqueness to discard data.
- The brief Phase A source-table locks can delay registration/profile writes.
  Measure migration time on staging and use a reviewed operator window/checkpoint.
- A legacy mapping conflict aborts the migration. Investigate it; do not force
  ownership or rewrite historical records to make the backfill pass.
- Commercial company limits are absent by the explicit scope contract. Paid
  multi-company exposure requires its separate product-access stage.
- Operator account transfer/archiving and feedback eligibility beyond the original
  creator are future workflows, not implicitly provided here.
- Local PostgreSQL tests use Auth stubs and SQL JWT claims. Real Supabase
  Auth/PostgREST behavior still needs separately authorized staging rehearsal.
- The V1 cleanup script refuses databases containing account tables before any
  cleanup transaction. Account-aware deletion needs a separate reviewed procedure.

## Validation

`python3 scripts/test-account-foundation-local.py --container ai-diagnostic-v21a-foundation`
uses a disposable PostgreSQL 17 container with no published ports. It creates and
removes only random test databases, never a remote connection. It exercises the
actual full migration chain and broad V1 history fixtures; exact before/after
snapshots permit only the company account_id addition. The signup/owner/RLS tests
include anonymous, unverified, administrator-nonowner, revoked and foreign actors;
actual V1 save/submit operations are exercised without real providers.

To repeat from the repository root, create a dedicated disposable container:

```sh
docker run -d --name ai-diagnostic-v21a-foundation --network none \
  -e POSTGRES_HOST_AUTH_METHOD=trust postgres:17-alpine
python3 scripts/test-account-foundation-local.py --container ai-diagnostic-v21a-foundation
docker rm -f ai-diagnostic-v21a-foundation
```

Wait for PostgreSQL readiness before running the script. The trust setting is
limited to this disposable container with no network or published ports. The
runner rejects other container prefixes, non-PostgreSQL images and published
ports. It cleans up its own randomly named databases even after test failure.

Focused application tests cover company selection, IDOR, profile revisions,
service-role report/PDF access, revocation during PDF preparation and plural admin
projections. Scope boundary tests exclude methodology/ledger mutation, team and
commercial tables. No real OpenAI, Resend, cleanup or deployment is executed.
